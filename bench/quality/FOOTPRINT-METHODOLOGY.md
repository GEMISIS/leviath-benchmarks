# Context Footprint Suite — methodology

*The published quality benchmark for Leviath. The performance track
(memory / throughput / cold start) is documented in the repo-root
METHODOLOGY.md; this document covers the context-economics claim only.*

---

## The thesis under test

**Structured context keeps each request's footprint small and stable;
a flat window grows with the work.** More tokens with less caching is
more expensive — that part is arithmetic. The consequential claim is
one step further: a small, stable per-request footprint is what makes
*cheaper models viable* — economy API tiers, and local models whose
context windows are 8k–32k where an unbounded flat window simply does
not run. Cost reduction starts with fewer tokens per request.

Leviath is an agent **runtime**, not a harness and not a coding agent;
both sides of every comparison are this runtime running published
blueprints, and no comparison to any other tool is made or implied.

## What is measured

1. **Tokens per request over the run** (headline): input and output
   tokens of every provider request, from the run's own journal —
   plotted per arm as stability vs growth, against reference lines at
   common local-model window sizes (8k / 32k / 128k). The summary
   number is `input_growth` (late-run mean ÷ early-run mean): ~1.0
   means the footprint holds; >1 means it grows with the work.
2. **Token composition and cache behavior**: cache reads vs writes vs
   full-price prompt vs output, and the cache hit rate — the tradeoff
   stated openly: structure currently bills fewer tokens at worse
   prices, flat bills more tokens at cheap cached rates.
3. **Wall-clock time**, total and per request (journal timestamps),
   at concurrency 1 so runs are comparable.
4. **Dollars**, priced from rates pinned per round, and
   **cost per functional success**.

All of it against a **functional** success bar, not perfection: the
program compiles and plays; the injected failures are found; the
architecture document is grounded and mostly right. Details are still
recorded strictly — scoring is generous, measurement is not.

## The tasks

Three tasks, one per agent family, chosen to be recognizable workloads
rather than puzzle boxes:

| task | family | functional bar |
|---|---|---|
| snake-cpp | coder | compiles (`c++ -std=c++17`) and ≥3 of 4 scripted `--test` scenarios pass |
| log-search | log-analyzer | ≥3 of 4 incident facts exactly right (root service, config key, T0, propagation) over a multi-MB generated corpus with a known injected failure chain |
| explain-repo | researcher | architecture document with ≥85% of cited paths/symbols actually existing (mechanical grounding — a fabricated citation is a detected hallucination, no judge needed), ≥60% of the auto-derived crate checklist covered, and a passing coherence read |

- log-search's corpus is generated by a committed, seeded generator
  whose answers are re-derived from the emitted files by an independent
  parser (`generate.py --check` is byte-identical).
- explain-repo is **repo-parameterized** (`repo.json`: path + pinned
  commit); the default target is the Leviath checkout itself. For any
  published round, a pinned third-party repository can be swapped in so
  accuracy is externally checkable.
- snake-cpp's spec requires a headless `--test` mode (seeded,
  scripted moves, machine-readable end state) — the acceptance
  interface is part of the task, which is also just good engineering.

## The arms

Identical to the standing quality-track discipline: the same runtime
binary on every side; `flat` (one window, oldest-first eviction) and
`flat-compacting` (summarize-on-overflow — what production harnesses
do) generated from the structured blueprints with `check_pairs.py`
enforcing identical tools, prompts, and budgets; the Leviath arm is the
composed cross-vendor **flagship** — the configuration the runtime
recommends — with its stage→model map frozen and published. Native
windows (footprint stability needs no artificial pressure), one pinned
headline model on the flat arms, concurrency 1.

## Honesty rules

Carried over unchanged: freeze-before-running (`qbench-*` tags; smoke
rounds stamped UNFROZEN-SMOKE and never publishable; freezing a counted
round commits to publishing its result), no run selection, seeded
subsets, exact small-sample statistics, cache-honest accounting from
provider-reported usage, secret scrub, raw trees published whole. The
caching tradeoff is called out in every cost table rather than
netted away; provider premium tiers above ~200k prompt tokens are
disclosed as an error in the *baseline's* favor.

## Successor benchmarks (deliberately split out)

This suite replaced the Context Retention Suite, which tried to carry
three claims at once. The other two are rebuilt separately, after this
one ships:

1. **Retention / window-pressure suite** — does structure preserve
   working knowledge when the window genuinely overflows? Needs
   irreducibly textual tasks (the semantic cross-document conflicts
   built for docs-audit, long multi-module builds) and the
   probe-replay machinery, all of which stays in the tree
   (`core/lvr.py`, `core/assemble.py`, `run_probes.py` — dormant) or
   in git history (the CRS tasks live at commit `5507baf` and its
   ancestors).
2. **Hallucination suite** — two pre-registered hypotheses from the
   2026-08-14 calibration runs: (a) structured context reduces reader
   hallucination rate (observed 20.0% vs 24.2%, p=0.33 — direction
   only), and (b) Opus-built contexts hallucinate more than
   Sonnet-built ones under an identical fixed reader (observed 30–48%
   vs 20–27%, the strongest pattern in the data).
